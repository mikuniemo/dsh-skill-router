# 方法论：把 Agent 技能目录从 O(n) 常驻降到 O(1) 路由

> 本文是 [dsh-skill-luyou](../README.md) 的设计文档。目标不是解释怎么用——README 负责——
> 而是把**每一个设计决策背后的失败模式与测量数据**写清楚，使你可以在另一个 harness
> （Claude Code、Codex、其他 agent 框架）上从第一性原理重新推导出同一个工具。

---

## 0. 问题陈述

Agent harness 普遍采用「技能目录」模式：每次请求都把可用技能的
`name + description` 注入上下文，让模型知道有什么可用。

这个模式的成本是 **O(技能总数)** 且**每请求都付**。实测（真实 1,246 技能库）：

| 常驻技能数 | 目录开销/请求 |
|---:|---:|
| 50 | ~5,000 tok |
| 235 | ~23,400 tok |
| 1,246 | **~70,800 tok** |

关键认知：目录进入 **cached prefix**，所以它主要是**上下文窗口问题**而不是计费问题。
200K 窗口被吃掉 35%；128K 窗口直接爆掉。缓存让它便宜，但不让它变小。

**目标**：常驻 O(1)（一个 ~600 token 的路由器），技能本体按需加载。

---

## 1. 核心机制：三级渐进披露

```
第 1 级  skill-router（常驻 ~600 token）
         只说"共 N 个技能、M 类、每类去哪读索引"

第 2 级  read skill-index/<类别>.md（1–4K token，按需）
         该类所有技能：名字 + 一句话 + 完整路径

第 3 级  read <技能>/SKILL.md（真正的指令正文）
```

模型判断任务属于哪一类，**只加载那一类**。不用不付费。

**适用性判断**：这个模式在技能数 > ~10 时开始净赚（路由器自身有固定成本）；
低于这个数，原生全量目录反而更简单。工具的 `plan` 命令会算这笔账。

## 2. 五个失败模式（每个都真实踩过）

### FM-1：移动技能产生死路径

**做法**：把实体目录放进扫描根，再用脚本「移出去」。
**结果**：索引记录的是 `<skillsRoot>/<name>/SKILL.md`，而下一步正好把这个目录移走。
路由器指向空气，模型得出「本机没有技能」。
**实测**：junction 挂载的技能路径 100% 有效，实体目录挂载的 100% 死路径。

**修复原则**：**永远不移动，只链接**。链接（Windows junction / POSIX symlink）放进
「off 根」，索引记录链接的 **target**（源库路径，永不移动）。删除链接不影响目标。

### FM-2：只管一个扫描根

DSH 实际扫描 **5 个根**（rank 100–500）：

| rank | 来源 | 路径 |
|---:|---|---|
| 100 | project-dsh | `<projectRoot>/.dsh/skills` |
| 200 | project-agents | `<projectRoot>/.agents/skills` |
| 300 | custom | `Config.customSkillDirs` |
| 400 | user-dsh | `<dshHome>/skills`（跳过 `.system` 子目录） |
| 500 | user-agents | `<agentsHome>/skills` |

只管 rank 400 的工具对其它四个根里的技能无能为力——它们照样常驻照样烧 token。
`<projectRoot>` 的定义是「最近的含 `.git` 的祖先目录，否则 cwd」。

### FM-3：扫描是一层的——必须精确镜像

DSH 只识别 `<root>/<name>/SKILL.md` 和 `<root>/<name>.md`，
**嵌套的 `**/SKILL.md` 刻意不发现**。工具的计数必须与 DSH 一致，
否则「为什么这个技能没生效」永远查不清。

更隐蔽的是**静默失效**：frontmatter 不合法的技能被整个跳过，
只在日志里留一条 warning，模型侧零提示。两种真实世界的文件形态会触发：

1. UTF-8 **BOM** 在 `---` 之前
2. `/* ... */` **注释横幅** 在 frontmatter 之前（作者的库里有 14 个技能这样死了）

工具必须同时做到：解析时容忍这两种形态（不漏数），报告时列出它们（可修复）。

### FM-4：没有预算的分类器等于没有分类

朴素的「`subdomain` 字段 → 名字前缀 → `other`」分类，在真实 1,548 技能库上
把 **489 个**塞进 `other`，产生一个 ~25,100 token 的索引文件——
**路由器方案的成本与它要替代的目录一样高**。

**修复原则**：分类必须**预算驱动**而不是分类学驱动：

1. 信号优先级：外部 override → `metadata.category` → `subdomain` → 名字前缀 → `other`
2. 超过预算的桶**拆分**：
   - 先按「名字中最具区分度的 token」拆（最多 2 层，且必须均衡 ≥20%）；
   - 之后无条件按**字母序装箱**——按实测 token 打包，**一轮必收敛**。
3. 过小的桶（<120 token 且 <3 个技能）并入 `other`，防止路由表膨胀
4. 桶名去重（`-2`、`-3`…），防止两次独立拆分产生同名文件互相覆盖

**重要教训**：不限层的 informed split 会产生
`--not-security--not-services--not-agentic--...` 这样的 20 段长链，
每层只剥掉几个技能，永远不收敛。字母序装箱看似「不智能」，
但它按预算打包，**保证收敛**——工程上，可收敛的笨办法胜过不收敛的聪明办法。

### FM-5：token 计算的两个坑

1. **不建模描述上限**。DSH 的 `catalogDescriptionMaxLength` 默认 500，
   超长描述被截断。不建模会高估 ~3%（实测 595,650 vs 578,548 字符）。
2. **对 CJK 用「4 字符/token」**。英文近似成立，中文**一个字约一个 token**。
   必须按脚本分频统计，分别计价。

## 3. 移植到其它 harness 的检查清单

在任何采用「技能目录」模式的 harness 上复刻此方案，按顺序回答：

1. **扫描根有哪些？**（DSH：5 个，含 project/custom/user 三层）
2. **发现深度？**（DSH：一层；嵌套刻意忽略）
3. **frontmatter 硬性要求？**（DSH：`name` + `description` 必需，缺则整个技能静默跳过）
4. **catalog 每条的渲染格式与描述上限？**（DSH：`` - `name`: desc ``，上限 500）
5. **有没有原生的「隐藏但不失效」开关？**
   （DSH：没有——`disable-model-invocation: true` 会连 loader 一起挡。
   Claude Code 等若有，可先用原生开关，超出后再上本方案。）
6. **链接类型**：Windows 用 junction（免管理员权限），POSIX 用 symlink。

前四问的答案决定 `roots.mjs` / `catalog.mjs` 的常量；
第五问决定是否需要本方案；第六问决定 `mount.mjs` 的实现。

## 4. 验证方法

- **沙箱端到端测试**（`test/smoke.mjs`，24 条断言）：
  临时目录里构造「正常技能 + BOM 技能 + 注释横幅技能 + 缺 name 技能 + 嵌套技能」，
  走完 scan → plan → apply(dry) → apply → 幂等重跑 → verify → restore 全流程，
  断言链接数、文件内容、源库完好、幂等性、死路径为零。
- **真实库验证**：在作者 1,495 技能的真机上跑 `plan`（只读），
  断言 0 桶超预算、最大桶恰在预算线上、分类数合理（60）。
- **不变量**：`restore` 之后源库逐字节完好（junction 删除不影响 target）。

---

## 5. 已知边界

- 依赖模型主动性：弱模型可能不读路由器。路由文本已显式写明规则，
  但这是模式本身的代价，不是实现缺陷。
- 多一跳 `read` 对比原生 `skill` 工具。用 ~70K token 换一次文件读取，值。
- 插件自带技能（`includeDefaultRoots: false` 的隔离域）设计上不可见，不覆盖。
- 源库更新后索引不自动同步；重跑 `apply`（幂等、增量）。

---

## 6. 一句话版本

> **不要移动技能，链接它们；不要相信分类学，相信预算；不要猜测 token 数，
> 建模渲染格式；不要只管一个目录，枚举全部扫描根。**
